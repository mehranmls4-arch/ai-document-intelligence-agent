# Database

Runtime ORM: **Drizzle** (`lib/db/schema.ts`), database: SQLite via `better-sqlite3` (`lib/db/client.ts`). See the README's "Why Drizzle, not Prisma" section for why `prisma/schema.prisma` exists but is not used at runtime.

Migrations live in `drizzle/` (SQL files generated by `npx drizzle-kit generate`) and are applied by `scripts/migrate.ts` (`npm run db:migrate`), which uses Drizzle's own `migrate()` function — no external binary involved.

## Tables

### `documents`
Core record for every upload. `id` (uuid), `filename`/`originalFilename`, `fileType`, `fileSizeBytes`, `storagePath`, `documentType` (enum-as-text: `INVOICE`/`PURCHASE_ORDER`/.../`UNKNOWN`), `classificationConfidence`, `status` (enum-as-text: `UPLOADED`/`PROCESSING`/`EXTRACTING`/`CLASSIFYING`/`VALIDATING`/`NEEDS_REVIEW`/`COMPLETED`/`FAILED`), `failureReason`, `extractedText`, `pageCount`, `extractionMethod` (`pdf_text`/`ocr`), `extractionConfidence`, `extractedAt`, `overallConfidence`, `needsReview`, `createdAt`/`updatedAt`.

### `invoices`
One-to-one with `documents` (`documentId` unique + FK, cascade delete). Vendor/invoice/date/currency/PO/amount fields, `paymentTerms`, and `fieldConfidenceJson` (a JSON string of per-field confidence scores — kept as JSON rather than a column per field since it's write-once-per-extraction and read as a whole object by the UI).

### `invoice_line_items`
Many-to-one with `invoices` (cascade delete). `description`, `quantity`, `unitPrice`, `amount` — all plain reals/text, no derived columns (the validation engine recomputes `quantity * unitPrice` on read rather than trusting a stored product).

### `validation_results`
Many-to-one with `documents` (cascade delete). `rule` (a stable string identifier like `TOTAL_MISMATCH`), `status` (`PASSED`/`WARNING`/`FAILED`), `message` (human-readable). Re-running validation deletes and re-inserts this document's rows rather than appending — the table holds the *current* validation state, not a full history (history of what a human did about it lives in `review_actions` instead).

### `review_actions`
Many-to-one with `documents` (cascade delete). `fieldName`/`originalValue`/`correctedValue` (all nullable — populated for `FIELD_CORRECTION`, null for `APPROVE`/`REJECT`/`SEND_BACK`), `action` (`FIELD_CORRECTION`/`APPROVE`/`REJECT`/`SEND_BACK`), `reviewer` (free text, no auth), `notes`, `createdAt`. This table is append-only — it's the audit trail, and nothing ever deletes from it.

### `processing_runs`
Many-to-one with `documents` (cascade delete). `stage` (`UPLOAD`/`EXTRACTION`/`CLASSIFICATION`/`STRUCTURED_EXTRACTION`/`VALIDATION`/`AI_ANALYSIS`/`REVIEW`/`COMPLETED`), `status` (`STARTED`/`SUCCEEDED`/`FAILED`/`SKIPPED`), `startedAt`/`completedAt`, `durationMs`, `errorMessage`. Append-only per pipeline run — re-processing a document adds a new set of rows rather than overwriting the old ones, so the full processing history for a document is visible, not just the latest run.

### `ai_analyses`
One-to-one with `documents` (`documentId` unique + FK, cascade delete). `summary`, `keyObservationsJson`/`anomaliesJson` (JSON string arrays), `provider`/`model` (which `AIProvider` produced this, for traceability if you switch providers later).

## Relationships

All foreign keys cascade on delete (`onDelete: 'cascade'`), configured in `lib/db/schema.ts` and enforced by SQLite's `PRAGMA foreign_keys = ON` (set in `lib/db/client.ts` — SQLite does not enforce foreign keys by default, this has to be turned on explicitly per connection). Deleting a `documents` row cleans up its `invoice` (and that invoice's `invoice_line_items`), `validation_results`, `review_actions`, `processing_runs`, and `ai_analyses` automatically.

## Verified

A standalone smoke test (`scripts/db-smoke-test.ts`) creates a document → invoice → line item → validation result → processing run, retrieves the document with all relations nested via Drizzle's relational query API, and asserts every relation is present, before cleaning up. This has been run and passes. The full pipeline has also been exercised via real HTTP uploads (see the README's Testing table), which exercises every table's real read/write path, not just this synthetic smoke test.

## Moving off SQLite

Every column type used here (text, integer, real, boolean-as-integer, timestamp-as-integer) has a direct Postgres equivalent. To move to Postgres: swap `drizzle-orm/better-sqlite3` for `drizzle-orm/node-postgres` (or another Postgres driver) in `lib/db/client.ts`, change `dialect: 'sqlite'` to `'postgresql'` in `drizzle.config.ts`, regenerate migrations, and point `DATABASE_URL` at a real connection string. No schema redesign is needed.
